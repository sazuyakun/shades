Shades code structure

Monorepo: apps are the products, packages hold the shared code. Every app and package has its own CLAUDE.md.
shades/
├── CLAUDE.mdrules for the whole repo
├── apps/
│ ├── mac/Shades.app: the thin shell
│ │ ├── CLAUDE.md
│ │ ├── project.ymlXcodeGen makes the Xcode project
│ │ ├── ShadesApp.swiftapp start, windows, menus
│ │ └── Assets.xcassetsicon (placeholder for now)
│ ├── web/website + download (stack later)
│ │ └── CLAUDE.md
│ └── mcp/helper Claude Desktop launches
│ └── CLAUDE.md
├── packages/
│ └── ShadesKit/all the real code
│ ├── CLAUDE.md
│ ├── Package.swiftlists the modules + who uses whom
│ ├── Sources/
│ │ ├── ShadesCore/the edit in memory
│ │ ├── ShadesCommands/every edit = a command
│ │ ├── ShadesDocument/save / load .shades
│ │ ├── ShadesMedia/import, thumbnails
│ │ ├── ShadesEngine/playback + Metal
│ │ │ └── Shaders/*.metaleffects (Claude can add)
│ │ ├── ShadesColor/grading, scopes
│ │ ├── ShadesGraphics/titles, templates
│ │ ├── ShadesAudio/mixer, ducking
│ │ ├── ShadesCaptions/transcripts
│ │ ├── ShadesExport/rendering files
│ │ ├── ShadesMCP/MCP server for Claude
│ │ └── ShadesUI/all the screens
│ └── Tests/one test folder per module
└── docs/PLAN · DESIGN · UX · ARCHITECTURE · LAUNCH

ShadesCorethe edit itself · depends on nothing
  • Arrows only go down. Core knows nothing about screens or Claude, so it stays simple and testable.
  • Screens and Claude sit side by side at the top. Both change things only through Commands.
  • The app is thin. If code isn't about windows or menus, it goes in a module.
  • The compiler enforces it: a module can't use one above it, or the build fails.
